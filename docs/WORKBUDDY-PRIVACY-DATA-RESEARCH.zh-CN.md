# WorkBuddy 向外发送的用户隐私数据：AgentReins 专题研究底稿

> 研究日期：2026-09-22  
> 原则：区分“发给记忆检索服务”和“发给大模型”，区分“网络正文已证实”和“本地上下文记录显示”。公开材料不披露用户真实凭据、完整记忆或可识别个人的信息。

## 一、当前可以确认的结论

WorkBuddy 发送的内容不止是用户在输入框中键入的文字。现有证据显示，上下文可能由 WorkBuddy 在模型调用前自动装配，并包含工作区信息、记忆机制、连接器状态和持续会话历史。

| 数据类别 | 已观察到的具体内容 | 来源 | 触发方式 | 接收方 | 证据强度 |
|---|---|---|---|---|---|
| 用户当前指令 | `<user_query>` 中的原始输入 | 用户输入框 | 用户主动 | 大模型 | 网络正文已证实 |
| 系统行为规则 | Agent 身份、执行规范、工具与内容规则 | WorkBuddy 内置模板 | Agent 自动装配 | 大模型 | 网络正文已证实 |
| 记忆机制说明 | 记忆类型、保存条件、检索和使用方法 | WorkBuddy 内置模板 | Agent 自动装配 | 大模型 | 网络正文已证实 |
| 记忆检索查询 | WorkBuddy 组装的 Recall Query | 当前上下文 | 首次模型请求前自动触发 | 腾讯记忆检索接口 | 网络正文已证实 |
| 工作区绝对路径 | `/Users/<user>/WorkBuddy/<workspace>/` | 本机工作区 | Agent 自动装配 | 模型上下文记录 | 本地记录已证实 |
| 项目结构快照 | `<project_layout>` 中的目录结构 | 当前项目 | Agent 自动装配 | 模型上下文记录 | 本地记录已证实 |
| 本机时间与时区 | 精确日期、时间和 GMT+8 | 本机运行环境 | Agent 自动装配 | 模型上下文记录 | 本地记录已证实 |
| 连接器状态 | GitHub、Agent Mail 等连接状态 | WorkBuddy 配置 | Agent 自动装配 | 模型上下文记录 | 本地记录已证实 |
| 记忆存储路径 | 全局及项目级 `MEMORY.md` 路径 | WorkBuddy 配置 | Agent 自动装配 | 大模型/上下文记录 | 网络与本地证据 |

| 历史助手回复 | `<previous_assistant_message>` | 当前会话历史 | 持续会话自动携带 | 模型上下文记录 | 本地记录已证实 |
| 工具参数和结果 | `<previous_tool_call>`、`<result>` | 文件读取、命令、连接器等工具 | 模型触发后由 Agent 回填 | 后续模型上下文 | 本地记录已证实 |

| 长期记忆正文 | 用户偏好、账号、项目和环境资料 | `~/.workbuddy/MEMORY.md` 等 | Recall 命中或上下文注入 | 可能进入模型上下文 | 尚未由当前网络样本证实 |

## 二、三个值得公开展示的实测事实

### 1. 一句短输入不等于一个短请求

2026-09-21 的网络实验中，用户输入很短，但 WorkBuddy 先向 `agenttool/v1/intent/recall` 发送了 13,615 字符的检索文本，约 10 秒后才调用 `v2/chat/completions`。

该模型请求包含：

- 15,693 字符的 System Message；
- 13,313 字符的 Memory 规则块；
- 470 字符的运行时提醒；
- 71 字符的用户指令包装块。

这说明界面上的一句话只是完整出境上下文的一小部分。

### 2. 发送 `hello` 也会暴露环境元数据

AgentReins 的 WorkBuddy 本地上下文记录显示，一次内容仅为 `hello` 的请求仍携带：

- 当前工作区的绝对路径；
- 项目结构快照；
- 精确时间和时区；
- 已连接的连接器名称及状态；
- 全局记忆与项目记忆的绝对路径；
- 何时写入用户长期记忆的规则。

这些内容与回答问候并无直接必要关系，适合成为专题中的“数据最小化”案例。

### 3. 持续会话会放大隐私暴露面

现有本地证据库中：

| 上下文特征 | 记录数 |
|---|---:|
| 包含项目上下文 | 181 |
| 包含连接器状态 | 206 |
| 包含记忆与技能提醒 | 549 |
| 包含历史用户消息 | 24 |
| 包含历史助手消息 | 24 |
| 包含历史工具调用或结果 | 24 |

一条约 64,000 字符的持续会话上下文中，AgentReins 检测到 120 处用户目录绝对路径、17 个 IPv4 形式字符串和 40 个凭据相关关键词。这里的数字用于说明暴露面，不代表其中每一项都是有效秘密；该样本还需要网络正文复核后，才能作为“实际发给模型”的最终证据。

## 三、不能提前下的结论

当前网络基线中的 Recall 返回 `results: []`，因此不能据此声称 WorkBuddy 已把完整 `~/.workbuddy/MEMORY.md` 发给大模型。

本机该文件约 39 KB，目录涉及用户偏好、API 凭据、GitHub 账号、项目资产、云服务器和内网环境。这证明风险后果可能很高，但不等于这些正文已经在当前样本中出境。专题必须通过可控记忆命中实验完成最后一段证据链。

同样，HTTP 中的 `role: "user"` 不能直接解释为“用户主动提供”。WorkBuddy 把 Memory 规则和系统提醒也放在 User Message 内，必须按实际来源重新分类。

## 四、下一轮可复现实验

使用无真实意义的合成标记，避免为了研究再次泄露真实隐私：

```text
WB-MEMORY-CANARY-20260922-A
WB-PROJECT-CANARY-20260922-B
WB-FILE-CANARY-20260922-C
```

实验分四组：

1. 将 A 放入全局记忆，将 B 放入项目记忆，将 C 放入普通项目文件。
2. 新建 WorkBuddy 会话，仅发送 `。`，观察首次 Recall Query 和首次模型请求是否包含 A/B/C。
3. 发送与 A 语义相关、但不直接复述标记的问题，观察 Recall 是否命中及其结果是否进入后续模型请求。
4. 明确要求读取普通项目文件，观察模型工具调用、文件读取结果和下一次模型请求之间的因果链。

每个标记都要记录五个时间点：本地读取、Recall 请求、Recall 响应、模型请求、模型响应。只有标记出现在解压后的模型请求正文中，才能判定为“已发送给大模型”。

## 五、专题建议

这组研究适合拆成四篇，而不是把所有风险堆在一篇文章里：

1. 《你只输入一句 Hello，WorkBuddy 还发送了什么》
2. 《AI Agent 的记忆是谁主动读取的：模型，还是 Agent》
3. 《历史对话、工具结果和项目路径如何进入下一次模型请求》
4. 《39 KB 用户记忆会不会出境：一次可复现的 Canary 实验》

AgentReins 的价值应落在“内容级证据”上：展示具体类别、必要片段、来源、触发者、接收方和完整因果链，而不是只展示 Token 数或一个风险标签。
