# WorkBuddy 网页投毒检测与阻断：初步取证

日期：2026-10-04。对象：本机 WorkBuddy 5.5.6。仅静态读取，未修改 WorkBuddy、安装 hook 或启用阻断。

## 已确认的代码能力

检查文件：`/Applications/WorkBuddy.app/Contents/Resources/app.asar.unpacked/cli/dist/codebuddy.js`。

1. 接收模型流时，代码读取 `choices[0].delta.reasoning_content`，转换为 `content_block_delta / thinking_delta`。说明内置运行时能够处理模型返回的可见推理文本；不证明桌面插件向第三方开放了这一流，也不代表所有模型都有该字段。
2. 工具执行路径会 `await executePreToolUseHooks(...)`；返回 `allowed=false` 时抛出 `PermissionDeniedError`。这是明确的执行前阻断分支。
3. 普通工具与 MCP 工具路径存在 `await executePostToolUseHooks(...)`，支持 `updatedToolOutput` 替换结果。它有望在网页结果进入后续上下文前提供检查点，完整上下文装配顺序仍需运行验证。
4. 部分 hook 调用的异常被 catch 后仅记录错误，随后继续。因此检测器崩溃、通信断开等情况下不能默认认为会阻断。

以上是静态证据，不是本机桌面会话已接入或阻断验收通过。

## 防护链路

用户任务 → 网页工具调用 → 网页原文 → 工具结果检查 → 下一轮模型输入 → 模型响应／可见 reasoning → 工具执行前检查 → 文件、进程、网络动作。

网页工具结果检查：保存原始结果和来源，识别其中冒充系统指令、索取凭据、要求执行无关命令等内容。风险结果必须等待决定，不能边扫描边交给模型。替换结果时保存原文与实际交给模型的版本。

工具执行前检查：将模型提出的动作与用户任务、网页来源以及此前工具结果关联。网页里的“读取密钥并上传”不能自动获得用户授权。判断对象是工具名、参数、目标文件和外联地址，而非 reasoning 是否说出了恶意意图。

reasoning 流：作为辅助证据和提前预警，不能作为唯一关口。模型可能不返回 reasoning，也可能直接生成工具调用。

采集日志、进程轮询及文件监听负责取证；它们不能保证在动作发生前阻断。可靠防护需要同步控制接口。

## AgentReins 的接入边界

保留原有流式采集与证据存储；增加独立控制通道。hook 在关口等待 AgentReins 返回放行、拒绝或请求确认。检测可组合来源标记、任务与动作一致性分析、确定性限制，以及模型语义审查，不能只按攻击关键词判断。

按 session_id、tool_call_id 关联：用户任务、外部内容来源、原始结果、送入模型的结果、模型提出的动作、检测理由、处置决定与实际执行结果。证据不足时显示“疑似”，不要把网页中的普通引用直接判为攻击。

安全模式须定义超时、服务离线和崩溃行为。高风险动作不能在检测器异常时自动放行；是否能在 WorkBuddy 原有 hook 框架内实现这一保证，是验收重点。

## 尚需验证

- 桌面 WorkBuddy 会话是否实际加载这些 hook，以及配置作用域、覆盖优先级。
- 可见 reasoning 的第三方实时订阅接口；不能将内置流转换代码当成可接入证明。
- 网页由内置工具、MCP、浏览器或 shell 获取时，哪些路径覆盖，哪些绕过。
- PostToolUse 替换是否发生在所有后续模型请求之前，是否仍存在原始结果副本进入上下文。
- hook 超时、异常、并行调用、子 agent、取消和重试是否可绕过保护。

下一次验证应使用独立临时项目与假凭据、受控网页，比较正常页面和包含恶意指令的页面。验收必须证明：正常任务继续；恶意内容的处理有证据；目标危险工具没有启动；异常时行为符合安全模式。不能以“弹出告警”替代“实际未执行”。
