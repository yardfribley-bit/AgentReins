## 1. 测试环境与边界

每个新验收用例创建独立 UUID 临时目录和 SQLite 数据库，退出时关闭连接并回收该目录。仅使用合成内容 hello、second 等；不写生产证据库，不修改 Agent 配置，不启动真实 Agent 任务，不向真实审计服务器发送数据。

测试运行于当前 macOS 开发环境、Swift debug 构建。调试构建时延不能直接作为产品性能承诺。后续性能验收需记录硬件、构建模式、磁盘余量、冷暖缓存、样本规模和后台负载。

故障注入采用测试数据库中的 SQLite 触发器，使指定写入返回 ABORT。它验证事务失败回滚，不等价于断电或强制终止进程。数据库关闭再打开验证连接级恢复，不等价于进程崩溃恢复。

## 4. 性能与长期运行方案

采用渐进负载；下面是待执行计划，不是已测结果：

- 小规模：1,000 个事件，建立功能和时延基线。
- 中规模：10,000、100,000 个事件，分别含短正文与大正文分布。
- 大正文：单条 1 MiB、10 MiB，并观察单记录是否突破批次时间预算。
- 并发：实时接收同时浏览历史、展开原文、运行导出；分别测单任务和多 Agent。
- 积压：暂停解析消费者再恢复；持续实时负载期间观察历史暂停原因和最长等待时间。
- 长期：至少一次 2 小时受控负载；后续试点再做 24 小时运行。
- 检索：正文大小分布、常见/稀有关键字、短词/长词、时间范围与来源筛选、并发查询；分别记录索引积压、索引体积、查询 P50/P95/P99，并与 `LIKE` 基线对照。不能只测小型热缓存或只报平均值。

采集接收、解析、查询、上传分别记录 P50/P95/P99；记录峰值 RSS、CPU、数据库锁等待、写事务耗时、WAL 大小、磁盘写入量、队列数量/字节/最老年龄。

先确定硬性正确性门槛，再根据目标硬件冻结性能阈值。比较改造前后必须使用相同样本和工作负载；每组记录重复次数及原始测量，不将一次运行的快慢当成稳定结论。

当前已有一项 10,000 文件/10,100 事件的代码索引基准；它只度量内存索引过程，不代表数据库历史读取、实时采集或整体性能。

### 确认缺陷：同会话越序（P1）

复现：
1. 保存会话 session 的第一条证据。
2. 领取工作并标记暂时失败，设置退避时间。
3. 保存同会话的第二条证据。
4. 再次领取工作，第二条被返回；预期应等待前驱。

原因：claimParseJob 按就绪时间筛选，没有同会话前驱约束。  
影响：后续任务投影若依赖有序输入，可能先处理结果再处理其前置事件。  
修复方向：持久化分区及单调接收顺序，领取时只允许该分区可处理的头部；不同分区继续执行。隔离缺口是否允许越过须依解析器是否能恢复状态明确决定。

旧测试 testRetryDoesNotBlockAnotherRecord 使用同会话样本并期待越序，与 V2 要求冲突；它的通过不能证明设计正确。应在整改时改为不同会话隔离测试，并保留本轮同会话阻塞验收。
