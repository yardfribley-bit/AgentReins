# WorkBuddy 数据出境清单

> 一句“我想写一个微信公众号发布 Skill”，为什么会向上游模型提交 82,433 tokens？

**作者：AgentReins 安全研究**  
**事件时间：2026 年 9 月 21 日**

我原本只是想验证 WorkBuddy 的推理过程。

2026 年 9 月 21 日 01:22，我在 WorkBuddy 中输入了一句很短的需求：

> 我想写一个微信公众号发布 skill

这句话只有十几个汉字。按照直觉，模型需要知道的无非是：我要创建什么 Skill、目标发布渠道是什么、最终交付 Markdown、Word 稿还是自动发布工具。

但 AgentReins 捕获到的事实完全不同。

WorkBuddy 第一次请求上游模型时，提交了 **82,433 个输入 token**。其中 **80,896 个 token 被标记为缓存内容**。随后几轮请求的输入继续增长到 86,335、88,200 和 91,152 tokens。

真正属于本轮的新需求只有一句话。其余内容来自系统指令、个人记忆、Agent 身份文件、项目背景、历史对话、历史工具调用和本机环境。

这不是一篇根据界面截图推测的文章。本文结论来自 WorkBuddy 本机 trace、AgentReins 原始证据数据库和模型返回的 token usage。我们要回答的不是“模型是不是在思考”，而是一个更具体的问题：

> 当用户向 AI Agent 提出一个普通需求时，究竟有哪些本地数据跟随上下文一起离开了电脑？

## 一次普通请求的完整时间线

AgentReins 将本轮操作还原为以下链路：

| 时间 | 可观察行为 | 输入 token | 输出 token | Reasoning token |
|---|---|---:|---:|---:|
| 01:22:56 | WorkBuddy 构造模型请求 | 待模型返回 | — | — |
| 01:23:15 | 模型要求调用 `Skill`，加载 Skill 创建规范 | 82,433 | 899 | 859 |
| 01:23:45 | 模型调用 `AskUserQuestion`，确认“发布”的含义 | 86,335 | 1,851 | 1,579 |
| 01:24:44 | 模型连续调用 `TaskCreate`，建立 5 个子任务 | 88,200 | 2,881 | 2,395 |
| 01:24:49 | 模型调用 `TaskUpdate`，推进任务状态 | 91,152 | 44 | 14 |

这条链路说明 WorkBuddy 的外显决策过程是合理且可还原的：先加载 Skill 规范，再识别需求歧义，向用户追问，然后拆分任务。

但另一个问题更值得关注：在第一次真正执行动作之前，输入上下文已经达到 82,433 tokens。

从第一次模型调用到 `TaskUpdate`，输入又增加了 8,719 tokens。也就是说，即使用户没有重新输入一段长文本，工具结果和中间对话仍在持续扩大下一轮需要提交给模型的上下文。

## WorkBuddy 实际向模型提交了什么

WorkBuddy 的本地 trace 中，`generation.toolInput` 保存了模型请求的前 100,002 个字符。将这部分请求拆开后，可以确认至少包含以下数据。

### 一 系统指令和 Agent 能力边界

请求开头不是用户问题，而是一组篇幅很大的系统指令，包括：

- Agent 的总目标和行为规范；
- 文件系统与互联网访问能力；
- 工具调用规则；
- Skill 搜索、安装和安全审计规则；
- 浏览器操作规则；
- Word、PPT、Excel 等办公能力路由；
- MCP 和运行时依赖配置；
- 如何向用户提问以及何时继续执行。

这部分内容决定 WorkBuddy 如何行动，属于正常的 Agent 控制上下文。但它也构成了产品自身的行为指纹：第三方模型服务可以从中了解 WorkBuddy 的工具体系、控制逻辑和安全边界。

### 二 三层记忆体系的规则

请求中存在约 3,808 bytes 的 `memory_system` 内容，明确描述了 WorkBuddy 的三层记忆架构：

1. Cloud Memory；
2. 用户级本地记忆 `~/.workbuddy/MEMORY.md`；
3. 工作区记忆 `.workbuddy/memory/`。

它不仅告诉模型“有记忆”，还告诉模型这些记忆保存在哪里、什么情况下读取、什么情况下写入，以及哪些内容应当跨项目保存。

这些规则本身不一定包含秘密，但会暴露本机数据组织方式和 Agent 的持久化策略。

### 三 跨项目用户记忆

请求中存在约 6,088 bytes 的 `user_memory`。

其中包括：

- 用户主要使用中文；
- 用户喜欢结论先行、证据链和量化指标；
- 用户在歧义情况下偏好的协作方式；
- GitHub 账号使用约定；
- 不可逆操作前的核查习惯；
- 测试服务器禁止留下持久后门；
- 本机用户名和常用工作目录；
- 设备、系统和开发环境信息；
- 多个长期项目之间的关系。

用户记忆的作用原本是让 Agent 更懂用户。但本轮任务只是创建一个微信公众号发布 Skill，其中绝大多数跨项目资料并不是完成任务所必需的。

### 四 Cloud Memory 工作画像

请求中还包含约 5,766 bytes 的 Cloud Memory 摘要，内容分为“工作背景”“个人背景”“当前关注”和“近期动态”。

它记录了用户正在推进的多条项目线，例如：

- AgentReins；
- redteam-elite-pack；
- CoPyRIT；
- fleet-monitor；
- SkillHub 安全审计；
- Voyager 部署；
- Mac 异常重启排查。

这部分记忆还出现了具体基础设施和环境信息，包括：

- 腾讯云服务器 `43.153.166.155`；
- 局域网设备 `192.168.1.39`；
- 服务器 `165.154.226.119`；
- macOS 设备型号 MacBookPro16,2；
- 本机用户名 `jatsmith`；
- Ubuntu、Caddy、systemd、Docker 等部署组件；
- GitHub 账号和仓库用途；
- `authorized_keys`、`systemd`、`useradd` 等安全约束。

这里需要强调：这些信息并不是模型通过扫描电脑临时发现的，而是 WorkBuddy 已经整理进长期画像，并在构造本轮模型请求时自动注入。

### 五 Agent 身份文件

请求中约 5,256 bytes 的 `identity_context` 包含三份文件：

- `~/.workbuddy/SOUL.md`
- `~/.workbuddy/IDENTITY.md`
- `~/.workbuddy/USER.md`

`SOUL.md` 定义 Agent 的人格和行为原则；`IDENTITY.md` 定义 WorkBuddy 如何认识自己；`USER.md` 则记录它如何理解用户。

这些文件的存在有助于保持 Agent 的连续性，但它们也意味着：每次与模型交互时，用户画像和 Agent 身份可能被一起交给模型服务，而不仅仅保留在本地。

### 六 本机环境和工作区信息

模型请求还包含：

- 操作系统为 macOS；
- Shell 为 `/bin/zsh`；
- IDE 主题；
- 当前 Workspace 的绝对路径；
- 当前项目结构；
- 当前时间；
- GitHub、Agent Mail 等 Connector 的连接状态。

这些信息中的一部分对编程任务有用，但在“创建公众号发布 Skill”这样的任务中，项目绝对路径、连接器状态和大量工作区信息未必必要。

### 七 历史对话和工具调用

在 trace 保留下来的请求前缀中，我们统计到至少：

- 21 个 `previous_user_message`；
- 58 个 `previous_assistant_message`；
- 72 个 `previous_tool_call`；
- 12 个 `<user_query>`。

历史内容涉及磁盘空间检查、Downloads 目录盘点、删除 DMG/ISO/EXE、Kiro 数据目录分析、后台任务通知以及此前的工具输出。

这意味着模型收到的不是“当前问题加少量最近对话”，而是一段规模很大的历史执行记录。

部分工具结果被替换为 `<omitted />`，这减少了原始结果的暴露，但工具名称、命令参数、操作目标、任务编号和对话意图仍可能保留在上下文中。

## 敏感信息扫描结果

我们对本地 trace 已保存的请求前缀进行了模式扫描。结果如下：

| 敏感指标 | 出现次数 | 说明 |
|---|---:|---|
| IPv4 地址 | 18 | 包含云服务器和局域网地址，可能存在重复 |
| GitHub | 24 | 包含账号、仓库和操作约定 |
| 服务器相关描述 | 26 | 包含部署环境和资产用途 |
| `root` | 5 | 可能来自服务器上下文或命令记录 |
| 密钥相关描述 | 1 | 发现“密钥”语义，不等于发现有效密钥值 |
| `authorized_keys/systemd/useradd` | 10 | 来自服务器安全规则和历史背景 |
| 明文 `password/密码` | 0 | 在已保存的请求前缀中未发现 |
| 身份证、银行卡、住址 | 0 | 在已保存的请求前缀中未发现 |

我选择不隐藏上述 IP、用户名和项目名称，是为了真实展示模型上下文中包含了什么。需要特别说明的是：本文没有在已保存的前缀中发现明文密码，也没有证据证明某个仍然有效的 API Key 被包含在本轮请求中。

但“没有发现”不能被解释为“完整请求一定没有”。原因是 WorkBuddy 的 trace 对 `toolInput` 做了截断。

## 100002 字符之后发生了什么

两次 `generation.toolInput` 的长度都精确停在 100,002 个字符。转成 UTF-8 文件后，已保存部分约为 115,974 bytes。

这不是自然结束。第二次请求的尾部直接终止在历史任务文本中，说明原始请求仍有后续内容，只是本地 trace 没有继续保存。

与此同时，模型返回的 usage 显示首次输入为 82,433 tokens。仅凭 100,002 个字符通常无法完整承载 82,433 tokens 的中文、英文、JSON 和工具历史。因此可以确认：

> 模型实际接收的上下文大于 AgentReins 当前能够从 WorkBuddy trace 中还原的内容。

这形成了一个重要的取证缺口。我们能够证明哪些内容已经进入请求前缀，却不能证明被截断部分还包含什么。

## 这是否属于数据泄露

从技术角度看，可以确认发生了数据外发：本地和云端记忆、身份资料、历史对话以及环境信息进入了发往上游模型 `Hy3` 的请求。

但“数据泄露”需要进一步判断授权、目的、服务条款、数据保留策略和接收方身份。本文不直接给出法律结论。

更准确的安全定性是：

### 过度上下文共享

当前任务与服务器资产、其他项目进度、GitHub 使用约定、Mac 异常重启等信息没有直接关系，但这些信息仍进入了模型上下文。

### 数据最小化不足

Agent 没有根据当前任务选择最小必要记忆，而是倾向于注入一个内容广泛的用户画像和长历史记录。

### 跨项目边界模糊

用户在 A 项目中积累的记忆，可能在 B 项目的普通任务中被自动带出。长期记忆提高了便利性，也扩大了单次请求的暴露半径。

### 上游身份仍需验证

模型响应中的 `model` 字段是 `hy3`，WorkBuddy 界面和 trace 将其显示为 Hy3。但仅凭这一字段，无法独立证明最终执行推理的真实模型、基础设施运营者和数据落点。

### 历史工具证据扩大攻击面

工具调用不仅记录“做过什么”，还可能携带路径、命令、目标地址和工具结果。当这些记录进入下一轮上下文时，一次过去的敏感操作可能被反复提交给模型。

## Reasoning token 不是思维链正文

本轮模型分别返回了 859、1,579、2,395 和 14 个 reasoning token。

这些数字只能证明模型为相应轮次计入了多少内部推理 token。响应中没有 `reasoning_content`，因此 AgentReins 无法恢复这些 token 对应的逐字内部思考。

我们能够可靠还原的是“可观察决策轨迹”：

```text
读取 Skill 创建规范
→ 判断“发布”存在歧义
→ 向用户追问
→ 创建 5 个子任务
→ 更新任务状态
```

将这条轨迹称为“完整思维链”是不准确的。安全产品应该区分三件事：

1. Hidden reasoning：模型内部使用了多少推理 token，正文是否可得；
2. Visible reasoning summary：模型向用户明确表达了什么；
3. Decision evidence：模型随后调用了哪些工具、参数是什么、结果是什么。

对于安全审计而言，第三项往往比隐藏思维链更可靠，因为它可以被独立验证。

## 为什么普通日志看不到 AgentReins 却能发现

这次发现并不是依赖单一日志字段得出的。

如果只看 WorkBuddy 界面，用户只能看到自己的短指令、Agent 的回答和少量工具状态；如果只看某一条 prompt 事件，也只能看到当前轮次新增的用户问题和系统提醒。真正的数据出境范围隐藏在多个证据源之间。

AgentReins 将以下证据进行了关联：

- WorkBuddy 原生 session、turn 和 trace ID；
- `generation.toolInput` 中的实际模型请求前缀；
- 模型返回的 input、output、cached 和 reasoning token usage；
- `Skill`、`AskUserQuestion`、`TaskCreate`、`TaskUpdate` 等工具调用；
- 本地记忆、身份文件和 Workspace 路径；
- 模型请求与后续行为之间的时间关系。

通过交叉比对，AgentReins 发现：当前轮次表面上的短 prompt 只是增量，真实模型请求还拼接了长期记忆、身份信息和大段历史上下文。82,433 input tokens 与被捕获的上下文结构相互印证，证明这不是一次普通的短问答请求。

这也是 AgentReins 与传统进程监控、网络连接列表或聊天记录导出的区别：

> 它不是只告诉用户“WorkBuddy 访问了模型”，而是继续回答“访问时携带了什么、来自哪里、为何进入上下文，以及随后影响了哪些决策”。

单一采集源可能只保存当前 prompt，也可能对大字段进行截断。AgentReins 的价值在于通过多源证据关联重建真实链路，并明确标注哪些事实已确认、哪些内容因上游截断仍不可见，而不是把局部日志包装成完整真相。

## 数据出境清单应该怎样呈现

未来每一次模型请求都应该自动生成一张数据出境清单，而不是让用户阅读十万字符的原始 JSON。

本次事件的清单应该类似这样：

```text
Agent：WorkBuddy
上游模型标识：Hy3
用户原始需求：我想写一个微信公众号发布 skill
首次输入：82,433 tokens
缓存内容：80,896 tokens

已包含：
✓ Cloud Memory
✓ User Memory
✓ SOUL.md
✓ IDENTITY.md
✓ USER.md
✓ 历史用户消息
✓ 历史助手回复
✓ 历史工具调用
✓ 本机环境与绝对路径
✓ GitHub 与 Connector 状态
✓ 服务器和项目资产信息

敏感发现：
• IPv4 地址 18 次
• 服务器相关描述 26 次
• GitHub 相关内容 24 次
• root 相关内容 5 次
• 未在已保存前缀中发现明文密码

必要性判断：大量内容与当前任务无直接关系
证据完整度：部分，toolInput 在 100,002 字符处截断
```

用户还应该能够继续展开，看到每条数据的来源和传播路径：

```text
~/.workbuddy/USER.md
→ WorkBuddy Context Builder
→ Hy3 模型请求
→ 后续 AskUserQuestion / TaskCreate 决策
```

只有把“来源—上下文—接收方—后续用途”串起来，用户才能真正判断这次外发是否必要。

## Agent 产品需要建立哪些边界

### 默认最小化记忆注入

不是所有长期记忆都应该进入每一轮请求。系统应先根据任务检索相关记忆，再只提交完成任务所需的片段。

### 明确区分记忆作用域

个人偏好、项目记忆、基础设施资产和高敏凭据必须采用不同的作用域和默认策略。跨项目调用高敏记忆时，应当提示用户或要求授权。

### 在请求发送前生成预览

对于包含服务器地址、密钥、身份文件或其他高敏信息的请求，Agent 应提供“即将发送的数据”摘要，而不是等请求完成后再审计。

### 保存完整性元数据

即使出于性能原因不能保存全部正文，也必须记录原始长度、截断位置、哈希、字段清单和丢失范围。否则用户看到的“完整上下文”可能只是片段。

### 验证模型和中转身份

不能只信任响应里的 `model` 字段。应结合请求域名、TLS 证书、ASN、IP 归属、响应特征和模型行为指纹，区分官方端点、OpenRouter、企业网关和未知中转。

### 对工具结果实施数据流跟踪

文件读取、网页内容、MCP 结果和 Shell 输出进入上下文时，应标记来源；后续被提交给模型或其他工具时，应形成可查询的数据传播链。

## 结论

这次事件没有证明 WorkBuddy 窃取了密码，也没有证明 Hy3 恶意保存了用户数据。

它证明的是另一件更基础、也更普遍的事实：

> 用户以为自己只提交了一句话，Agent 实际提交的却可能是一个由长期记忆、身份文件、历史任务、工具记录和本机环境拼装而成的巨大上下文包。

AI Agent 的便利，来自它能够记住用户、理解项目并调用工具；AI Agent 的风险，也来自同样三件事。

安全产品不能只盯着最终命令是否危险。它还必须回答：

- 用户输入了什么；
- Agent 又补充了什么；
- 哪些记忆被带入上下文；
- 数据最终发给了谁；
- 工具读取了哪些本地内容；
- 哪些内容在下一轮继续传播；
- 最终结果是否经过独立验证。

这就是 AgentReins 接下来要补齐的能力：不是把 Agent 的每一次操作变成难以阅读的日志，而是为每一次模型请求建立一份用户真正能看懂、也能验证的**数据出境清单**。

## 证据边界

本文基于 2026 年 9 月 21 日保存在本机的 WorkBuddy trace 和 AgentReins evidence 数据库。关键证据包括：

- WorkBuddy trace：`trace_330f847b128a4539b4646b8d2866306f.json`；
- WorkBuddy 首次模型请求 usage：82,433 input tokens、899 output tokens、859 reasoning tokens；
- trace 中 `generation.toolInput` 的本地保存上限：100,002 个字符；
- 模型标识：`hy3`。

本文能够证明上述内容进入了 WorkBuddy 构造的模型请求，并能够证明本地 trace 存在截断。本文不能仅凭这些证据证明上游服务的数据保留时长、真实基础模型身份、地理存储位置以及被截断部分的完整内容。
