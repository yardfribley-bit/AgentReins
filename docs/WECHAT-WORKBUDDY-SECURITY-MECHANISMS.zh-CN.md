# WorkBuddy 安全机制

> AgentReins 从真实模型上下文、Skill 规则和工具执行记录中，还原一个 AI Agent 如何保护用户文件，以及这些保护是否真正生效。

**作者：AgentReins 安全研究**  
**分析时间：2026 年 9 月 21 日**

AI Agent 已经可以读取文件、执行命令、访问互联网，也能修改一个完整的软件项目。用户通常只能看到它给出的回复，却很难回答几个基础问题：它受到哪些安全规则约束；执行危险操作前是否真的询问了用户；所谓沙箱和备份究竟是产品机制，还是提示词中的一句要求。

AgentReins 对本机 WorkBuddy 的真实 trace、系统上下文、Skill 文件和工具调用记录进行了关联分析。结果显示，WorkBuddy 确实设计了一套围绕个人文件的安全规则，包括只读扫描、禁止危险递归删除、操作前确认、先备份、优先移入回收站和小批量执行。

更有价值的发现是：安全机制不能只看它是否写在系统提示词里，还要检查执行过程中有没有遵守。AgentReins 可以把“设计规则”和“真实行为”放在同一条证据链上比较。

## AgentReins 如何发现安全机制

传统终端日志只能告诉用户运行了哪条命令。进程监控可以看到 WorkBuddy 拉起了哪些子进程。网络监控可以记录它访问了哪个地址。这些证据都无法单独说明 Agent 为什么这样行动，以及它原本应该遵守什么限制。

AgentReins 将四类证据放在一起：

1. WorkBuddy 发给模型的系统上下文；
2. 当前任务加载的 Skill 和工具定义；
3. 模型实际发起的工具调用及其参数；
4. 文件、进程和网络层留下的执行结果。

这使得一次安全分析可以从“发现一条命令”前进到“还原一项安全控制”：规则从哪里来，什么时候触发，模型做了什么决定，工具最终有没有按照规则执行。

## 已确认的个人文件安全规则

在 WorkBuddy 的真实模型请求中，AgentReins 捕获到了完整的 `personal_files_safety` 规则。该规则把桌面、下载、文档、用户主目录和其他非项目目录定义为高风险区域。

它包含八项明确限制。

### 禁止危险递归删除

WorkBuddy 被明确要求不得对个人目录和系统目录使用 `rm -rf`、`del /S /Q`、`shutil.rmtree()` 或大范围通配符。即使用户坚持，也应拒绝清空桌面、下载、文档、用户主目录或系统目录。

这是一条系统级行为规则。AgentReins 已经确认它进入了模型上下文，因此模型在决定是否执行删除操作时可以看到这条限制。

### 首次扫描必须只读

当用户要求整理、查找重复文件或清理磁盘时，WorkBuddy 的第一阶段只能生成文件路径、大小和日期清单，不能直接移动、改名或删除文件。

这条规则把“了解现状”和“改变文件”拆成两个阶段，避免一句含糊的“帮我清理一下”直接触发破坏性操作。

### 模糊需求必须先问清楚

对于“清理电脑”“删除垃圾”这类范围不明确的指令，WorkBuddy 应先确认目标目录、文件类型和筛选条件，甚至不能直接开始全盘扫描。

AgentReins 可以从后续的 `AskUserQuestion` 或普通对话中检查它是否真正执行了确认步骤。

### 危险操作需要警告和授权

在执行删除等不可逆操作前，WorkBuddy 被要求：

- 明确显示危险警告；
- 列出每一个受影响的文件路径；
- 解释具体风险；
- 等待用户明确确认。

这不是笼统的“谨慎操作”，而是一项可以核验的流程。只要其中一步没有发生，AgentReins 就能标记策略没有完整执行。

### 修改前必须备份

WorkBuddy 的规则要求，在个人目录中移动、重命名或删除文件前，先建立备份，确认备份成功，并向用户说明备份位置。

这里必须区分两件事。AgentReins 已确认“先备份”存在于安全规则中，但规则存在不等于备份一定完成。只有出现真实复制操作、备份文件和成功结果，才能把状态升级为“执行已验证”。

### 优先移入系统回收站

WorkBuddy 不应直接永久删除个人文件。macOS 应使用系统回收站机制，Windows 应调用回收站接口，Linux 应使用 `gio trash` 或 `trash-put`。如果没有可用的回收站能力，系统应再次警告并取得第二次确认。

这项机制为误删提供恢复窗口，也是截图中 Safe-Delete 的证据来源。

### 每批最多处理十个文件

个人文件操作被限制为每批最多十个文件，并要求每批结束后验证结果，任何失败都应立即停止。

这项限制的作用不是提高速度，而是控制一次错误的影响范围。AgentReins 可以根据实际工具参数和文件事件数量判断 WorkBuddy 是否突破了批次上限。

### Windows 非 ASCII 路径限制

WorkBuddy 被要求避免为包含非 ASCII 路径的任务生成 `.ps1` 或 `.bat` 文件，防止编码错误破坏文件名。它应优先使用直接命令调用。

这是一项平台特定保护，说明安全机制不仅包含“允许或拒绝”，也包括对已知工程风险的规避。

## WorkBuddy 还有哪些安全边界

除个人文件规则外，AgentReins 还发现了其他控制机制。

### 工作模式权限边界

WorkBuddy 定义了 Agent、Plan 和 Ask 三种模式：Agent 模式允许执行；Plan 模式应先设计方案，得到确认后再执行；Ask 模式只能分析和读取，不能修改文件或运行命令。

这种模式本质上是一套用户授权边界。AgentReins 可以比较界面模式、模型上下文和真实工具调用，检查只读模式下是否出现写文件或命令执行。

### Skill 局部安全规则

AgentReins 在 WorkBuddy 的本地 Skill 中发现了更细粒度的安全要求。例如部分 Skill 规定，提交反馈、修改配置或取消操作前必须进行二次确认，反馈内容不得携带未脱敏的隐私信息。

这些规则只在相关 Skill 被加载后生效，因此安全分析必须记录本轮加载了哪个 Skill、版本是什么、它向模型增加了哪些约束。

### 内容安全规则

WorkBuddy 的系统上下文包含内容拒绝规则。这类规则能够证明模型收到了哪些行为限制，但不能仅凭提示词证明每一种输入都能被稳定拦截。要确认效果，还需要专门的对抗测试。

### Sandbox 运行组件

从进程关系中，AgentReins 能够识别 `sandbox-center` 等运行组件，也能将 Node REPL、代码执行宿主和 Sandbox 关联到 WorkBuddy 的运行图中。

目前这项证据能证明组件存在，尚不能独立证明它限制了哪些文件目录、网络地址、系统调用或子进程。要把“发现 Sandbox”升级为“验证隔离有效”，需要在受控环境中测试越权读取、外网访问和逃逸行为。

## 安全机制存在不等于真正生效

在历史磁盘清理任务中，WorkBuddy 先进行了只读盘点，随后向用户询问清理范围，也给出了危险警告。这些行为与其安全规则一致。

同一任务还出现了值得核查的差异：

- WorkBuddy 曾计划一次处理约 72 个 DMG 文件，高于规则规定的每批十个；
- 它提出过“移入回收站后立刻清空”，这会缩短 Safe-Delete 提供的恢复窗口；
- 当前证据没有证明每个目标文件在删除前都完成了可恢复备份；
- 清理脚本返回 `Moved 0` 后，WorkBuddy根据磁盘空间变化推断文件可能已被手动删除或由系统清理，但缺少逐文件结果证据。

这些差异不能直接证明 WorkBuddy 存在安全漏洞，却说明提示词约束不是强制执行器。模型可能理解规则，也可能在长上下文、连续对话或用户追加指令后偏离规则。

这正是 AgentReins 要解决的问题：把“Agent 被要求怎么做”和“Agent 实际怎么做”放在一起验证。

## 四级证据模型

为了避免把安全宣传写成安全事实，AgentReins 应给每项机制标注证据等级。

| 证据等级 | 判断标准 | WorkBuddy 示例 |
|---|---|---|
| 策略已发现 | 规则出现在系统上下文、Skill 或配置中 | 禁止 `rm -rf`、删除前确认 |
| 组件已发现 | 对应进程、工具或服务真实存在 | `sandbox-center`、AskUserQuestion |
| 执行已确认 | 工具调用和系统事件证明规则被执行 | 先只读盘点，再请求用户确认 |
| 效果已验证 | 独立测试证明危险行为被阻止或可恢复 | 拦截越权读取、从备份恢复文件 |

按照这一模型，不能把“提示词写了备份”直接显示为“自动备份成功”，也不能把“存在 sandbox-center 进程”直接显示为“沙箱无法逃逸”。

## AgentReins 能向用户展示什么

一次 WorkBuddy 安全机制分析，最终应该形成一张用户能读懂的控制清单：

```text
Agent：WorkBuddy
安全机制：个人文件保护
规则来源：系统上下文 personal_files_safety

已发现：
✓ 禁止危险递归删除
✓ 首次扫描只读
✓ 危险操作前确认
✓ 修改前备份要求
✓ 优先使用系统回收站
✓ 每批最多处理 10 个文件

本次执行：磁盘清理
✓ 完成只读盘点
✓ 请求用户确认范围
✓ 展示危险警告
△ 计划批次超过 10 个文件
△ 未发现逐文件备份成功证据
△ 永久清空会缩短恢复窗口

结论：安全策略存在，部分流程得到执行，备份与批次限制仍需验证。
```

用户点击任意结论后，还应看到对应的原始提示词片段、工具调用、命令参数、文件事件和时间线。这样一份报告既不会掩盖 WorkBuddy 已有的安全设计，也不会把未经测试的机制写成已经有效。

## 这项能力的价值

Agent 安全不能只统计风险事件。一个成熟的监督系统还需要理解 Agent 自己的防护体系。

当用户同时运行 WorkBuddy、Codex、Cursor、Claude Code 或其他编程 Agent 时，AgentReins 可以用同一套方法回答：

- 每个 Agent 声明了哪些安全规则；
- 哪些规则来自系统提示词，哪些来自 Skill 或 MCP；
- 本次任务触发了哪些保护；
- 模型是否绕过、遗忘或违反了规则；
- 最终拦截、备份和恢复是否经过独立验证。

这使 AgentReins 能够建立一份持续更新的 Agent 安全画像。用户看到的不再只是“发生了一个文件事件”，而是“WorkBuddy 原本应该先备份，但这次没有发现备份证据”。

## 结论

本次分析确认，WorkBuddy 并非毫无安全设计。它在系统上下文中建立了较完整的个人文件保护规则，并在部分真实任务中执行了只读扫描、风险提示和用户确认。

同时，安全规则主要依赖模型遵守。批次限制、备份成功和 Sandbox 隔离效果不能只靠提示词证明。

AgentReins 已经能够从真实证据中发现这些机制，并区分策略、组件、执行和效果。下一步是在界面中持续展示每项机制的证据等级，并通过独立测试确认它是否真正保护了用户。

## 证据边界

本文分析基于本机 WorkBuddy trace、模型请求中的系统上下文、本地 Skill 文件、历史工具调用以及 AgentReins 捕获的运行证据。

本文能够确认规则和组件是否被观察到，也能够确认部分操作流程是否发生。本文没有仅凭提示词宣称备份、沙箱隔离或危险命令拦截已经通过完整安全测试。所有“尚未验证”的结论均保留为待测试状态。
