# 我们抓到了 ZCode 的 5.8 万字 Reasoning：AI 编程 Agent 到底在想什么、做什么？

> 作者：AgentReins
>
> 让每个人都能看懂、验证并信任自己的 AI Agent。

当你对 AI 编程工具说一句“帮我做一个应用”，接下来发生了什么？

它如何理解你的需求？为什么选择某个技术栈？向模型发送了多少上下文？调用了哪些工具？从哪里下载依赖？修改了哪些文件？它说自己完成了，是否真的完成？

绝大多数时候，用户只能看到最后一句：

> 已完成。

但在这句“已完成”背后，Agent 可能已经经历了数十次模型请求、工具调用、文件修改和外部网络连接。

这一次，我们使用 AgentReins 对 ZCode 进行了一次真实任务取证。

结果比我们预想的更值得关注。

---

## 一次普通的开发需求

我们向 ZCode 提出了一个很普通的需求：

> 我想写一个给微信公众号发文章的应用。之前我在本地编译好了格式，但内容放到公众号后格式全部错乱，影响美观。

ZCode 随后开始规划并实现一个桌面应用。

从用户界面看，这只是一次正常的 AI 编程任务。但 AgentReins 从 ZCode 本地证据、工具记录、文件活动和系统网络活动中，还原出了更完整的执行过程。

本次会话中，AgentReins 观察到：

- 10 段 ZCode 本地记录的 reasoning；
- reasoning 合计 **58,631 个字符**；
- 最大单段 reasoning 达到 **42,294 个字符**；
- 18 次工具调用；
- 6 种不同工具；
- 18 次成功的上游模型请求；
- 单次模型输入从 38,280 tokens 增长到 64,086 tokens；
- 多个文件创建与修改；
- npm 依赖安装及外部镜像访问；
- 两次被权限策略拒绝的命令尝试。

这不再是一条简单的聊天记录，而是一条完整的 Agent 执行链。

## Reasoning 暴露了什么？

这里所说的 reasoning，是 **ZCode 明确返回并写入用户本机数据库的推理记录**。

它不代表模型服务端没有返回的隐藏思维，也不意味着 AgentReins 能够解密 HTTPS 或读取模型供应商内部数据。我们的原则很明确：只陈述本机真实存在、能够验证的证据。

这些 reasoning 让我们第一次能够回答：Agent 为什么这样做？

### 1. 它如何理解用户需求

ZCode 将用户的需求转化为以下目标：

- 接收本地 HTML 文件；
- 将 CSS 转换为微信公众号兼容的内联样式；
- 提供移动端宽度的实时预览；
- 将处理后的内容写入富文本剪贴板；
- 允许用户粘贴到微信公众号编辑器。

这一步很重要。

因为“用户说了什么”和“Agent 认为用户要什么”并不总是一致。Reasoning 为需求理解提供了可审计证据。未来如果最终产品偏离需求，我们可以回到这里判断：偏差究竟发生在需求理解、模型决策，还是工具执行阶段。

### 2. 它为什么选择 Electron

ZCode 比较了 Electron、Tauri 和 Python GUI，最后选择 Electron。

它给出的核心理由是：Electron 原生支持 HTML 富文本剪贴板，更适合微信公众号复制粘贴场景。

这是一条典型的技术决策证据：

| 决策 | 选择 | 主要原因 | 代价 |
|---|---|---|---|
| 桌面框架 | Electron | 富文本剪贴板支持成熟 | 安装包和运行内存较大 |
| CSS 转换 | juice | 可将样式规则内联 | 引入第三方依赖 |
| DOM 处理 | cheerio | 便于清洗和改写 HTML | 引入第三方依赖 |

用户不应该只看到“Agent 选择了 Electron”，还应该知道它为什么选择，以及这个选择引入了什么风险和成本。

### 3. 它形成了怎样的执行计划

ZCode 将任务拆成七个阶段：

1. 初始化项目并安装依赖；
2. 编写 HTML 转换管线；
3. 编写 Electron 主进程和 preload；
4. 编写渲染界面；
5. 创建测试样例；
6. 验证转换结果；
7. 启动应用并验证运行状态。

有了这份计划，AgentReins 就可以将“计划”与“实际执行”进行比较：

- 哪些步骤已经执行？
- 哪些步骤被跳过？
- 测试是否真的运行？
- Agent 是否在验证前就宣布完成？

这比单纯记录日志更有价值。日志告诉我们发生了什么；计划与执行的差异告诉我们任务是否可信。

## Reasoning 之外，Agent 实际做了什么？

Reasoning 只是 Agent 自己的陈述，不能直接作为安全结论。

因此，AgentReins 将它与工具、文件和网络证据进行了对照。

我们确认 ZCode 执行了以下操作：

### 创建项目目录

```bash
mkdir -p ~/.zcode/workspace/default/wechat-format/{lib,renderer,sample,test}
```

### 写入项目文件

观察到的文件包括：

- `package.json`
- `lib/transform.js`
- `main.js`
- `preload.js`
- `renderer/index.html`
- `renderer/renderer.js`
- `renderer/style.css`

### 安装第三方依赖

```bash
ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ \
npm install --no-fund --no-audit
```

这一条命令包含两个值得向用户解释的安全信号。

第一，Electron 二进制文件并非直接从默认上游获取，而是配置了第三方镜像。

第二，命令使用了 `--no-audit`，关闭了 npm 安全审计。

这不意味着该操作一定恶意，也不代表镜像一定不安全。但是对于一个 AI 编程 Agent 来说，**供应链来源发生变化和主动关闭漏洞审计，都不应该被埋在后台日志里**。

用户应该看到：

> ZCode 正在从第三方镜像安装 Electron，并关闭 npm audit。是否允许继续？

这才是安全产品应该提供的解释。

## 我们还发现了两次权限拒绝

在 Plan Mode 中，ZCode 尝试执行组合命令时，两次被策略拒绝：

> Plan mode only allows read-only, non-destructive tools.

随后，ZCode 将命令拆分后继续执行只读检查。

这次没有发现明显的恶意绕过行为，但这个过程揭示了一个非常重要的监控维度：

- Agent 是否意识到权限限制？
- 被拒绝之后尝试了多少次？
- 是否通过更换工具、拆分命令或启动子进程规避限制？
- 最终执行的动作是否与用户授权一致？

单独看一次失败命令没有意义。把“模型决策—权限拒绝—重试策略—最终结果”串起来，才是完整证据。

## 42,294 字符的单段 Reasoning 正常吗？

本次任务最大的一段 reasoning 达到 42,294 个字符。

它包含任务拆解、框架选择、代码设计、实现细节、工具安排和大量自我讨论。对于一个并不复杂的桌面工具，这种规模值得关注。

Reasoning 过长可能带来：

- 上下文成本上升；
- 重复规划和自我讨论；
- 重要需求被大量中间内容稀释；
- 后续代码、测试和验证可用的上下文空间下降；
- Agent 看似思考充分，实际上验证不足。

因此，AgentReins 不应该把 5.8 万字符直接扔给用户。

我们更应该生成这样的结论：

> ZCode 的本轮推理异常膨胀，最大单段约 42K 字符。主要内容集中在技术选型和实现规划，但存在重复讨论。建议关注上下文成本，并确认测试与独立验证是否得到足够资源。

用户需要的是结论和证据入口，而不是另一堵日志墙。

## 一个更关键的问题：它向大模型上传了什么？

Reasoning 很长固然值得关注，但从安全视角看，更重要的问题是：

> 在这 18 次模型请求中，ZCode 究竟把哪些本机数据发送给了上游？

AgentReins 还原出了本次任务的模型路由：

```text
Provider: account:zai-start-plan
Model: GLM-5.3
Endpoint: https://zcode.z.ai/api/v1/zcode-plan/anthropic
Transport: SSE
```

这说明模型请求并不是在本机完成，而是发送到了 ZCode 的远程模型服务。

### 已确认进入模型上下文的数据

初始上下文明确包含：

- 用户输入的完整需求；
- 工作目录：`/Users/jatsmith/.zcode/workspace/default`；
- 本机用户名所对应的绝对路径；
- 操作系统与架构：macOS / Darwin 25.5.0 x64；
- Shell：`zsh`；
- Node.js 版本；
- 当前目录是否为 Git 仓库；
- 当前 Git 状态。

随着任务继续执行，模型还需要接收前序对话和工具结果，才能决定下一步动作。结合本地消息、工具记录和逐轮 Token 变化，可以确认或高度确信后续上下文包括：

- ZCode 已经生成的 reasoning；
- 前序模型回复；
- 工具名称和调用参数；
- Bash 命令与返回结果；
- 创建文件的完整路径；
- 写入文件的代码内容；
- npm 安装状态；
- 权限拒绝信息；
- Todo 与实施计划。

换句话说，ZCode 发送给模型的并不只是用户输入的那一句需求，而是一个不断增长的任务工作集。

### 上下文规模有多大？

本次任务的模型使用记录如下：

| 指标 | 实测值 |
|---|---:|
| 成功模型请求 | 18 次 |
| 单次最小输入 | 38,280 tokens |
| 单次最大输入 | 64,086 tokens |
| 累计输入计费量 | 937,207 tokens |
| 累计缓存读取 | 908,160 tokens |
| 累计模型输出 | 24,032 tokens |

这里需要特别说明：累计输入量包含多轮重复上下文，并不代表上传了 937,207 个完全不同的 token。

但是，缓存读取量不断增长到六万多个 token，说明大量历史上下文被持续复用。Reasoning、工具结果和生成代码很可能随任务循环进入后续请求。

这就是上下文膨胀不仅影响成本，也影响安全的原因：一段敏感数据一旦进入会话，可能在许多后续轮次中继续存在。

### 本次没有发现哪些敏感数据？

安全分析必须同时说明“发现了什么”和“没有发现什么”。

本次任务开始时工作区为空，而且不是 Git 仓库。AgentReins 没有发现：

- `.git` 历史被读取或打包；
- 其他本地项目被扫描；
- SSH 私钥；
- API Key；
- 密码或 Authorization Header；
- 银行卡、身份证等个人敏感数据；
- RSA 私钥；
- 大型代码归档上传；
- 用户文档目录被遍历。

对本次会话中的高可信凭据特征进行扫描，命中数为 **0**。

因此，我们不能把这次行为描述成“窃取密钥”或“静默上传完整 Git 历史”。证据支持的结论是：ZCode 向上游发送了任务所需的本机环境、对话、代码和工具上下文，但当前没有发现高价值凭据或其他项目数据进入该链路。

### 为什么仍然存在安全风险？

即使没有发现密钥泄露，这条链路仍然存在四类风险。

#### 1. 本机身份和开发环境暴露

绝对路径暴露了本机用户名，同时上传了系统、Shell、Node.js 和工作目录信息。这些数据可以形成设备与开发环境指纹。

#### 2. 项目代码会持续进入模型上下文

Agent 写文件时，完整文件内容通常作为工具参数存在。为了继续执行任务，后续模型请求需要携带相关对话和工具结果。

本次主要是模型刚生成的新代码，风险相对有限；如果任务改为维护现有私有项目，源代码、配置文件和业务逻辑就可能进入相同链路。

#### 3. Reasoning 会扩大敏感信息传播半径

本次 reasoning 合计 58,631 个字符。Reasoning 不仅占用上下文，还可能复述之前读取到的路径、代码或敏感信息，使数据在后续轮次中继续存在。

#### 4. 无法逐字还原每次 HTTPS Request Body

ZCode 当前配置显示：

```text
modelIoFullRetentionEnabled: false
```

因此，我们能够确认模型端点、上下文结构、工具记录与 Token 规模，却没有每次实际 HTTPS 请求 Body 的完整逐字副本。

这意味着：

- “本机环境和任务上下文被发送给上游”可以确认；
- “第 N 次请求包含哪一行代码”目前不能完全证明；
- “上游保存多久、是否用于训练”无法仅凭本机证据判断。

### 本次数据流风险结论

我们将本次任务评估为：

> **中等风险，需要用户知情。**

更严谨的安全结论是：

> ZCode 将用户需求、本机环境指纹、工作目录、工具执行结果和任务代码上下文发送给 GLM-5.3 上游服务。未发现凭据、其他项目或 Git 历史被上传。由于完整模型请求 Body 未保留，无法逐字证明每轮上传内容。

这类结论比“安全”或“危险”两个标签更有价值。它告诉用户数据去了哪里、包含什么、证据有多强，以及我们仍然不知道什么。

## 为什么不能只相信 ZCode 自己的数据库？

这是本次测试最重要的结论之一。

ZCode 本地数据库能够提供非常有价值的语义证据：

- 用户输入；
- Agent 对需求的理解；
- reasoning；
- 模型与供应商；
- 工具名称和参数；
- 工具返回结果；
- Token 使用情况。

但这些数据本质上仍然是 **Agent 自己记录的证据**。

如果某个后台组件读取了 `.git`、创建了归档并上传到外部服务器，而这些行为没有写进任务数据库，仅靠读取 ZCode 数据库就可能得出错误结论。

因此，我们将证据分成两层。

### 第一层：Agent 自报证据

用于理解语义：它声称自己为什么做、准备做什么、调用了什么工具。

在 AgentReins 中，这类数据现在明确标记为：

```text
self-reported / unknown
```

它有价值，但不能单独证明真实系统行为。

### 第二层：独立系统证据

由 AgentReins 从 Agent 之外观察：

- 哪个进程读取了什么文件；
- 是否访问 `.git`、密钥或记忆文件；
- 创建了什么归档或密文；
- 连接了哪个域名和 IP；
- 上传了多少字节；
- 哪个子进程发起连接；
- 行为属于哪个任务和工具调用。

如果 Agent 声称只执行了 `node --version`，但系统侧看到它读取数百个 Git 对象并向陌生 OSS 上传 15MB 数据，两类证据之间的冲突本身就是高危事件。

真正可信的 Agent 安全，不是监听 Agent 怎么说，而是验证 Agent 实际做了什么。

## AgentReins 如何展示这次任务

针对这次 ZCode 任务，一个有效的用户界面不应该只显示“18 条工具日志”。

它应该首先给出一段人能看懂的摘要：

> ZCode 正在构建一个微信公众号 HTML 转换器。它选择 Electron，并安装了 `electron`、`juice` 和 `cheerio`。Electron 下载使用第三方镜像，同时关闭了 npm audit。当前已创建或修改 7 个主要项目文件。本轮 reasoning 共 58,631 字符，最大单段约 42K，存在上下文膨胀。功能尚需独立验证。

同时，还应该单独展示上游数据流：

> 本轮向 `zcode.z.ai / GLM-5.3` 发起了 18 次成功请求，单次最大输入 64,086 tokens。已确认上下文包含用户需求、本机环境、工作目录和任务执行记录；未检测到高可信凭据。由于完整请求 Body 未保留，证据可信度应标记为“Agent 自报 + 行为推断”，而不是“网络正文确认”。

然后允许用户逐层展开：

```text
用户需求
  ↓
Agent 对需求的理解
  ↓
技术决策与 Reasoning 摘要
  ↓
模型请求
  ↓
工具调用与完整参数
  ↓
文件变化
  ↓
外部网络与依赖来源
  ↓
测试结果
  ↓
独立验证
```

第一眼看懂，第二层验证，最底层查看原始证据。

这才是我们理解中的 Agent 态势感知。

## 我们正在解决的，不只是“看日志”

AI 编程工具正在获得越来越大的权限：读取代码、访问记忆、安装依赖、调用 MCP、连接服务器、修改生产环境。

问题在于，用户对 Agent 的信任仍然主要来自聊天窗口中的自然语言。

一句“已完成”，不能证明需求真的完成。

一句“只是读取”，不能证明没有上传。

一句“使用官方模型”，不能证明中转没有替换上游。

AgentReins 希望建立的是一条可以验证的证据链：

> 用户要求了什么 → Agent 如何理解 → 模型如何决策 → 调用了哪些工具 → 读取和修改了什么 → 访问了哪些网络 → 最终结果是否经过独立验证

让每个人都能看懂、验证并信任自己的 AI Agent。

这是 AgentReins 正在做的事情。

## 证据边界声明

本文数据来自一次真实的本机 ZCode 测试会话。

- Reasoning 指 ZCode 明确返回并保存到本地数据库的内容；
- 本文没有声称获取模型服务端未返回的隐藏思维；
- 本文提到的第三方镜像和 `--no-audit` 是安全审计信号，不等同于恶意定性；
- Agent 自报证据与操作系统独立证据必须分层展示；
- 当前实验结论只适用于本次可复核证据，不对所有 ZCode 会话作泛化判断。
