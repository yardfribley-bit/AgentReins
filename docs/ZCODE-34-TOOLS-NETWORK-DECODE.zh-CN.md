# 通过ZCode网络解码分析出34个ZCode工具

**副标题：用户只输入一个句号，模型为什么先收到一整张 Agent 能力地图**

作者：AgentReins 研究组  |  实验日期：2026 年 9 月 21 日

我在 ZCode 中只输入了一个中文句号：`。`

ZCode 没有读取文件，没有执行命令，也没有调用任何工具。但在这个几乎为空的请求背后，它向模型提交了 38,280 个输入 Token，其中 35,520 个来自缓存；请求携带 34 个工具的名称、用途说明和完整参数 Schema。仅工具定义序列化后就约 141,051 个字符，而这一轮真正执行的工具数量是 0。

这不是一篇把“工具定义”误写成“工具执行”的流量文章。本文要回答一个更有技术价值的问题：一个 AI Agent 在调用模型之前，究竟向模型暴露了怎样的本机能力地图？这张地图如何从 JSON Schema 变成真实的文件读取、Shell 命令、跨会话检索和多 Agent 工作流？

## 先说明：这里的网络解码不是破解 TLS

标题中的“网络解码”，指的是还原 Agent 发给大模型的结构化请求，而不是破解 HTTPS。

本次实验使用 AgentReins 读取 ZCode 自己在 TLS 加密前写入的 `model-io-*.jsonl`。该记录包含 provider body、消息列表、工具 Schema、响应文本、已返回的 reasoning、Token 用量，以及 request、trace、turn 等关联标识。整个过程没有安装 CA，没有修改系统信任库，也没有把 ZCode 流量导向中间人代理。

因此，本文能够证明的是：这些字段存在于 ZCode 本机保存的、准备发送给模型的 Model I/O 记录中。它不能证明服务端如何存储这些内容，也不声称获得了模型服务端未返回的隐藏思维链。

## 一个句号背后的请求

| 指标 | 实测结果 |
| --- | ---: |
| 用户真实输入 | `。`，1 个字符 |
| 模型 | `account:zai-start-plan/GLM-5.3` |
| 输入 Token | 38,280 |
| 缓存读取 Token | 35,520，约占 92.8% |
| 输出 Token | 296 |
| 有序消息 | 6 条 |
| 工具定义 | 34 个 |
| 工具 Schema | 约 141,051 字符 |
| 本轮工具调用 | 0 次 |
| 已记录 reasoning | 1,126 字符 |
| 最终响应 | 247 字符 |

请求中的 6 条消息包括 ZCode 身份、运行与安全规则、沟通和编码规范、日期提醒、用户输入，以及一份带本机路径的 Skill 清单。34 个工具则通过 `tools` 数组发送，每项至少包含工具名、面向模型的说明和输入参数 Schema。

这意味着模型收到的不只是“用户说了什么”，还收到“这个 Agent 能做什么，以及应该如何命令它去做”。

## 34 个工具到底是什么

### 第一组 文件、命令与互联网

1. **Bash**：执行 Shell 命令。必填参数是 `command`；还支持超时、后台运行、自然语言说明，以及一个特别值得注意的 `dangerouslyDisableSandbox` 字段。源码中的输入 Schema 将超时上限设为 600,000 毫秒，并为沙箱违规、命令注入、高风险组合等情况定义了错误码。
2. **Read**：读取本地文件，要求绝对路径，可指定起始行和读取行数。它是代码理解、配置审查和读取工具输出的基础能力。
3. **Write**：创建或覆盖文件，参数为 `file_path` 和 `content`。工具说明要求覆盖既有文件前先读取它。
4. **Edit**：对文件执行精确字符串替换，参数包括 `old_string`、`new_string`、`file_path` 和 `replace_all`。它要求当前会话先读取目标文件，并要求旧字符串精确匹配。
5. **WebSearch**：向搜索服务提交查询，可配置允许和阻止的域名。它把外部搜索结果带入 Agent 上下文。
6. **WebFetch**：获取指定 URL，将页面转换为 Markdown，再由一个小模型根据 `prompt` 提取信息。这意味着一次工具调用中还可能嵌套另一次模型处理。

这一组构成 Agent 最直接的读、写、执行和联网能力。风险不在于它们存在，而在于模型是否在不需要时也提前获得全部调用说明，以及权限层能否可靠拦住越界输入。

### 第二组 计划、任务与用户交互

7. **AskUserQuestion**：在确实需要用户决策时提出结构化问题。Schema 包含问题、答案、注释和元数据，必填字段是 `questions`。
8. **EnterPlanMode**：让 Agent 进入只规划、不实施的模式，用于非平凡任务开始前的方案探索。
9. **ExitPlanMode**：提交计划并请求用户批准，核心参数是 `plan`，还可声明后续允许的提示。
10. **TodoRead**：读取当前会话的任务列表。
11. **TodoWrite**：整体写入任务列表，每项包含内容、状态和优先级。
12. **TaskOutput**：读取后台任务输出。工具说明已经标记为 deprecated，但 Schema 仍被发送给模型，参数包含任务 ID、是否阻塞和超时。
13. **TaskStop**：停止后台任务，可接受 `task_id` 或 `shell_id`。

这些工具不一定直接触碰用户文件，却会改变 Agent 的控制流。尤其是 Plan Mode、后台任务和 Todo 状态，会影响一项任务何时开始执行、是否持续运行以及用户何时看到结果。

### 第三组 自动化与延迟执行

14. **CronCreate**：在当前工作区创建持久化定时任务。支持延迟分钟数、五段 Cron、固定间隔、最大运行次数、标题和提示词。
15. **CronList**：列出当前工作区中的定时自动化。
16. **CronUpdate**：按自动化 ID 更新定时任务定义，要求保留 ID 与历史记录。
17. **CronDelete**：按 ID 删除定时自动化。
18. **OffPeakCreate**：创建一次性错峰任务，在当前会话中等待服务端授予计算资源后无人值守运行，并携带完整会话历史。参数可指定模型、思考级别和权限模式。
19. **OffPeakList**：查看错峰任务状态与排队位置。

这组工具把 Agent 从“本轮对话中的即时程序”变成了“未来仍会运行的自动化主体”。对安全审计而言，时间维度非常重要：用户当前允许的上下文、权限和文件状态，可能与任务真正执行时已经不同。

### 第四组 多 Agent 与跨会话能力

20. **Agent**：启动子 Agent 处理复杂的多步骤任务。参数包含任务说明、完整 prompt、子 Agent 类型和是否后台运行。开源契约显示，后台模式会返回子会话 ID、后台任务 ID 和输出文件路径。
21. **SendMessage**：向另一个 Agent 发送消息，参数为目标 Agent、摘要和正文。工具描述特别说明，普通文本输出对其他 Agent 不可见，跨 Agent 通信必须显式调用该工具。
22. **ReadSessionContext**：读取另一个持久化 ZCode 会话的相关内容或交接摘要。它要求 `sess_*` 格式的会话 ID和检索问题，支持 `relevant` 与 `handoff` 两种策略，单次最多返回约 12,000 Token。

这一组直接触及两个常被忽略的边界：Agent 之间的数据流，以及过去会话到当前会话的数据流。源码证明 `ReadSessionContext` 不是笼统的“记忆”概念，而是一个带目标 session ID、查询语句、策略、Token 上限和引用信息的明确读取接口。

这也回答了一个重要问题：过去项目数据并不一定在每次请求中自动出现。它可能由 Agent 主动预装，也可能在模型调用 `ReadSessionContext` 后被读取，再进入下一轮模型请求。只有逐轮关联请求与工具调用，才能区分这两种路径。

### 第五组 动态工作流

23. **CreateWorkflow**：创建并运行 TypeScript 动态工作流，用普通控制流组织多个模型驱动的子 Agent，支持并发数、子 Agent 模型、脚本、路径和参数。
24. **AmendWorkflow**：修改既有工作流运行，创建一个替代旧运行的新 run，并复用已经完成的工作。
25. **SaveWorkflow**：将工作流脚本保存到项目 `.zcode/workflows` 或全局 `~/.zcode/workflows`，使它可以跨会话复用。
26. **EvalWorkflowSnippet**：同步编译并运行一小段工作流 TypeScript，用于在启动正式运行前验证解析、命令输出和控制逻辑。
27. **ListWorkflowRuns**：列出当前项目中的工作流运行及状态。
28. **GetWorkflowRun**：读取一次工作流运行的进度、Token 用量、日志尾部、最终结果或结构化失败信息。
29. **ResumeWorkflowRun**：恢复被停止、中断或因 provider 错误退出的工作流运行。
30. **ResolveWorkflowQuestion**：回答工作流子 Agent 在运行中升级出来的阻塞问题。
31. **ListSavedWorkflows**：列出项目级和全局保存的工作流定义。
32. **ListModels**：列出当前主机已配置的模型，为工作流子 Agent 指定 `providerId/modelId` 及 reasoning level。

动态工作流不是普通的“调用一个工具”。它允许模型生成一段 TypeScript 编排程序，再让程序扇出多个子 Agent、循环、判断、暂停和恢复。源码目录中存在工作流编译、沙箱、运行日志、并发治理、恢复、升级问答和产物发布等独立模块，说明这已经是一套小型 Agent 调度系统。

### 第六组 Skill 与 MCP

33. **Skill**：把某个 Skill 的专用说明加载进主会话。参数是 Skill 名称和可选参数。真实请求还单独发送了一份可用 Skill 清单，其中出现了本机绝对路径和插件缓存路径。
34. **mcp__node_repl__js**：来自 MCP 的 Node JavaScript 执行入口，限定为 Browser Use 与 Computer Use。参数包含代码、超时和标题。它不是 ZCode 核心工具契约中的普通内置项，而是运行时通过 MCP 注入的外部能力。

第 34 个工具揭示了工具集合的动态性：所谓“34 个 ZCode 工具”，准确说是本次实验请求中模型实际收到的 34 个工具，其中 33 个来自当时启用的 ZCode 能力面，另 1 个来自已连接 MCP。换一台机器、换一个插件配置或权限模式，数量可能变化。

## 从 Schema 到执行：源码中的真实调用链

ZCode 官方仓库把 Agent CLI、运行时和工具代码放在 `apps/zcode-cli`。工具契约集中在 `packages/contracts/src/tools`，入口文件导出了 Read、Write、Edit、Bash、Agent、Skill、自动化、计划模式、跨会话读取和动态工作流等定义。

一次工具调用大致经过以下链路：

| 阶段 | 发生了什么 | 安全意义 |
| --- | --- | --- |
| 1 模型请求 | ZCode 把工具名称、说明与 JSON Schema 放入请求 | 模型获得能力地图和合法参数格式 |
| 2 模型返回 | 模型返回 tool call、调用 ID 和参数 | 此时只是意图，不代表已经执行 |
| 3 调度与校验 | 运行时规范化参数、查找 registry、安排串行或并行执行 | 无效工具名或错误参数应在这里失败 |
| 4 权限与 Hook | PreToolUse、PermissionRequest 等策略介入 | 可以允许、拒绝或替换工具输入 |
| 5 本机执行 | 对应 handler 读取文件、执行命令或启动工作流 | 真正影响本机和外部系统的边界 |
| 6 结果持久化 | 保存调用状态、输出、耗时、错误与附件 | 形成审计证据，也可能写入本地敏感结果 |
| 7 再次入模 | 工具结果被追加到下一次模型请求 | 本机数据由此成为新的出境上下文 |

开源代码中的 `executeToolCallsForModelStep` 明确区分 pending、running、completed、error 等状态，把工具结果写入会话历史，然后通过 `commitTurnRequestEntries` 作为后续模型上下文。换句话说，真正的数据链条不是“模型调用了一次工具”这么简单，而是：

`模型提出调用 → Agent 权限判断 → 本机执行 → 结果落盘 → 结果再次发送给模型`

这正是网络层和本地运行时必须联合审计的原因。只看 HTTPS 连接，只能看到“连到了谁”；只看工具日志，又无法证明哪些结果最终进入了模型请求。

## 四个最值得研究的安全边界

### Bash 的沙箱旁路不是普通参数

真实 Schema 中存在 `dangerouslyDisableSandbox`。这个名字已经明确说明它不是常规业务参数。源码还定义了 `SANDBOX_VIOLATION`、`COMMAND_INJECTION_RISK`、`HIGH_RISK_COMBINATION` 等错误类型，说明开发者知道 Shell 执行需要专门的风险控制。

研究重点不应停留在“Bash 很危险”，而应验证：模型在什么提示下会生成该字段；权限模式是否始终要求用户确认；Hook 能否替换或拒绝输入；后台命令、管道和间接脚本是否走同一策略。

### ReadSessionContext 是历史数据进入新请求的清晰入口

该工具允许模型指定另一个会话 ID 和自然语言查询，并返回相关片段或交接摘要。这比“Agent 有记忆”更具体，也更容易审计。

研究时应记录：谁触发读取、读取了哪个会话、检索问题是什么、选择了哪些消息、是否截断、结果是否进入下一轮模型请求。这样才能回答“过去项目数据是 Agent 主动发送，还是模型要求读取”的问题。

### 动态工作流把模型输出变成可执行编排

CreateWorkflow 和 EvalWorkflowSnippet 允许模型提供 TypeScript。即使存在编译器与沙箱，它仍然扩大了攻击面：模型不仅选择工具，还能生成控制流，决定何时并发、重试、恢复和调用子 Agent。

审计对象因此从单次 tool call 扩展为：工作流源码、编译结果、运行 ID、子 Agent 输入、每个子任务的模型与 Token、升级问题、恢复点以及最终产物。

### MCP 让工具集合不再固定

`mcp__node_repl__js` 不在核心工具清单里，却出现在真实请求中。这证明工具集合由运行时环境决定。安装插件、连接 MCP 或加载 Skill，都可能改变模型可见的能力。

因此，安全产品不能只维护一张静态工具名单。它必须逐次保存模型实际收到的 Schema，并标注工具来自核心运行时、插件、Skill 还是 MCP。

## 为什么“发送定义但没有执行”仍值得关注

第一，它消耗上下文。此次工具 Schema 约 14.1 万字符，是请求体的主体。即使缓存降低了重复计费或延迟，它仍然参与模型上下文和能力选择。

第二，它暴露能力。模型在用户提出需求之前，就知道 Agent 能执行 Shell、跨会话读取、创建持久自动化、启动子 Agent、编排工作流和运行 MCP JavaScript。

第三，它扩大提示注入的选择空间。当网页、项目文件或工具结果中出现恶意指令时，模型拥有的高权限工具越多，攻击者可以诱导的动作种类越多。工具是否最终执行仍取决于模型、策略、权限和用户确认，但“可选动作空间”已经扩大。

第四，它削弱最小权限原则。对一个仅包含 `。` 的输入，任务所需工具数是 0，提供工具数是 34，实际调用数也是 0。按本次实验定义：

`工具利用率 = 实际调用工具数 ÷ 提供工具数 = 0%`

`无关能力暴露率 = 非任务所需工具数 ÷ 提供工具数 ≈ 100%`

这两个指标并不证明漏洞，却准确量化了上下文最小化不足。

## 更合理的设计：按需暴露工具

一个更保守的 Agent 可以采用分层工具发现：

1. 首次请求只发送用户输入和低风险元工具，例如工具目录搜索。
2. 模型表达明确需求后，由本地策略选择最小工具集合。
3. 高风险工具只发送简短能力摘要；真正调用前再加载完整 Schema。
4. 文件、Shell、跨会话、持久自动化和 MCP 工具分别设置独立权限域。
5. 每次请求保存“提供了哪些工具、为什么提供、实际用了哪些”的证据。

这种设计的目标不是让 Agent 变笨，而是让能力暴露与任务需要同步增长。解释文本不需要 Bash；读文件任务不需要 Cron；一次简单修改也不一定需要完整动态工作流系统。

## AgentReins 如何做这项审计

AgentReins 将 ZCode 的加密前 Model I/O 按 request ID、trace ID、session ID 和 turn ID 关联，分别保存：

- 用户输入、系统指令、历史消息、Skill 与 Agent 规则；
- 完整工具 Schema 和请求元数据；
- 模型响应、ZCode 本地记录的 reasoning 与 Token；
- 后续工具调用、参数、执行状态和结果；
- 工具结果是否进入下一次模型请求；
- 网络目标与本地证据是否能够相互印证。

这让审计从“上传了多少 Token”前进到“这些 Token 具体是什么、来自哪里、为什么发送、谁触发了后续读取，以及是否超出当前任务所需”。

## 证据边界

本文结论基于 2026 年 9 月 21 日一次真实 ZCode 请求，以及当日公开的 ZCode 仓库代码。34 是该次请求中的工具数量，不是所有安装环境永远固定的数量。

工具定义被发送，不等于工具已经执行。本轮实际工具调用为 0。本文也没有证明远端服务保留了这些数据，不能读取服务端未返回的隐藏推理，更不能仅凭系统指令中出现“memory”或“project”字样，就声称具体用户记忆或项目文件已经上传。

## 结语

一个句号没有要求 Agent 读文件、执行命令或启动工作流。但模型在回答之前，已经收到一张由 34 个工具组成的能力地图。

AI Agent 的安全问题，不只发生在危险工具真正执行的那一刻。更早的问题是：模型在什么任务下被告知了哪些能力，Agent 又在什么时点把本机数据带回模型上下文。

如果我们只统计 Token，就会错过其中最有价值的事实。只有把上下文、工具 Schema、权限决策、本机执行和下一轮模型请求连成一条证据链，才能真正看清 Agent 做了什么，也才能讨论什么叫合理的最小权限。
