# 审计上传 v2（十台终端试点）

## 已实现

客户端继续保留完整任务 JSON 的语义，但不再把大 JSON 当作每次 HTTP 请求正文。

1. 小对象（≤16 KiB）整体编码；较大对象递归拆分，大字符串按 UTF-8 字节拆成 ≤256 KiB 的块。
2. SHA-256 标识内容；任务版本保存根哈希，引用可复用的子块。
3. `probe` 每次最多查询 512 个哈希，只补传服务端缺失块。
4. `block` 上传一个块；服务端校验长度和哈希、原子落盘后回复。
5. `commit` 携带根哈希、设备身份及递增版本序号。服务端检查所有引用、任务范围，并在 SQLite 事务提交后确认。
6. 缺块返回 409，客户端重新探测；重试同一版本返回同一回执。旧版本不能覆盖新版本。

所有操作仍使用 HTTPS `/api/audit/ingest` 和原设备认证。块按设备隔离。
`queue-v2.json` 保留每个任务的上传进度，失败退避不阻塞其他任务；400/413/422 保留为拒绝状态，需排查后恢复，不丢弃证据。
旧 `queue.json` 和 `inflight.json` 只读迁移并保留，不能在新版运行后直接启动旧客户端，否则可能再次处理旧队列。

SQLite 保存任务摘要、版本、访问审计和根引用；正文块保存于数据库路径加 `.blocks` 的目录。
旧协议仍接受，新增相同正文通过 `snapshot_bodies` 去重；原有历史正文不自动重写或清理。
备份必须同时覆盖 SQLite（使用在线备份）和块目录；不得单独清理已引用块。

## 阅读接口

列表仅返回摘要。详情支持 `/cases/<id>/request|memory|relay|process`。
完整 JSON 在展开时才请求 `/cases/<id>/snapshot`，不再重复嵌入详情。

## 部署顺序与边界

- 先部署服务端（包括 `audit_blocks.py`），验证旧协议及 v2，再发布客户端。旧服务不识别 v2。
- 本次不变更历史任务上传边界，不自动回补历史。
- 这是**增量传输/去重存储**，不是最终的事件日志流：客户端仍在后台构建任务快照；服务端 commit 仍组装校验一次。完整快照不能作为千台规模的实时计算路径。
- 服务端组装有 512 MiB 累计读取预算、20 万节点访问和 64 层限制；一次最多组装一个任务，其余返回可重试 503。预算不是 JSON 文件大小承诺。
- 块留存/过期回收、设备配额、磁盘告警和租户级资源控制尚待实现。客户端块缓存目前不自动清理；不能据此宣称长期无人值守或千台规模就绪。
- 下一阶段改为带稳定 `event_id`、`task_id`、版本与正文引用的事件批次；服务端持续更新任务投影，RAG/检测异步消费新增事件。完整大 JSON 仅供导出与历史核对。

上线前须以十台实际终端验证峰值速率、断网重连、磁盘增长和服务端内存，不能用单元测试替代容量验证。
